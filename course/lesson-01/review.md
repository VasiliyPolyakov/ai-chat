## 3. Порівняння підходів

### 3.1. `HealthService` vs логіка в контролері

- **Твій підхід:** `HealthController` → `HealthService.check()`; сервіс інжектить конфіг і збирає відповідь.
- **Еталон:** лише контролер; конфіг інжектиться прямо в нього; сервісу немає.
- **Trade-offs:** сервіс — ще один файл і провайдер заради одного `return`; натомість контролер одразу тонкий, а місце для логіки перевірок уже є.
- **Чому так в еталоні:** YAGNI — порожня обгортка без логіки не потрібна; сервіс з'явиться в L02 разом із пінгом БД.
- **Коли твій кращий:** уже з L02 — `checks.db` піде в сервіс, контролер не зміниться.
- **Вердикт:** **рівноцінно, лиши своє** (в L02 ти все одно прийшов би сюди).

### 3.2. Конфіг: фасад `AppConfigModule` + `AppConfigService` vs `ConfigModule` напряму

- **Твій підхід:** `@Global()` `AppConfigModule` інкапсулює `ConfigModule.forRoot` (без `isGlobal`) і експортує лише `AppConfigService` з геттерами `port`, `version`, `databaseUrl`, `appEnv`, `isProduction`.
- **Еталон:** `ConfigModule.forRoot({ isGlobal: true, cache: true, ... })` прямо в `AppModule`; споживачі інжектять `ConfigService<Env, true>` і читають `get('X', { infer: true })`.
- **Trade-offs:**
  - Фасад: код не знає назв змінних і `@nestjs/config`; політики (`isProduction`) в одному місці; перейменування env — одна правка. Ціна — кожна нова змінна додається двічі (схема + геттер).
  - Напряму: менше коду, стандартний для документації Nest; але рядкові ключі й generic-и розтікаються по всіх споживачах.
- **Чому так в еталоні:** для 4 змінних і 2 споживачів обгортка — зайвий шар; namespace-конфіги (`registerAs`) еталон відкладає до L05–L08.
- **Коли твій кращий:** коли споживачів стане багато (L02 TypeORM, L05 auth, L08 LLM) і з'являться політики на `APP_ENV` (Swagger лише не в проді — L05).
- **⚠️ Що врахувати в L02:** фіксована точка `src/database/data-source.ts` для TypeORM CLI (міграції) працює **поза Nest DI** — `AppConfigService` там недоступний. Там доведеться прочитати `process.env` і прогнати ту саму функцію валідації. Тобто фасад покриває застосунок, але не CLI; не дублюй схему — перевикористай `validate()`.
- **Вердикт:** **рівноцінно, лиши своє.** Геттер `databaseUrl` поки ніхто не використовує — нормально, бо L02 близько.

### 3.3. Перетворення типів: `@Type(() => Number)` vs `enableImplicitConversion`

- **Твій підхід:** явний `@Type(() => Number)` лише на `PORT`; `plainToInstance` без опцій.
- **Еталон:** `plainToInstance(Env, raw, { enableImplicitConversion: true })` — конвертація всіх полів за TS-типами.
- **Trade-offs:** implicit — менше декораторів, але неявно: для майбутніх `boolean`-змінних рядок `'false'` стане `true` (непорожній рядок). Явний `@Type` — по декоратору на кожне нечислове/небулеве поле, зате поведінка видна в схемі.
- **Чому так в еталоні:** коротше; поки в схемі немає boolean, пастка не спрацьовує.
- **Коли твій кращий:** з першою boolean-змінною (`REGISTRATION_ENABLED` у L05). Там знадобиться `@Transform(({ value }) => value === 'true')`, а не просто `@Type(() => Boolean)` — бо `Boolean('false') === true` теж.
- **Вердикт:** **лиши своє.**

### 3.4. Перевірка формату `DATABASE_URL`

- **Твій підхід:** `@IsString() @IsNotEmpty()` — формат не перевіряється.
- **Еталон:** додатково `@Matches(/^postgres(ql)?:\/\//)` з власним повідомленням.
- **Trade-offs:** без перевірки опечатка `postgress://` або чужий URL пройде валідацію і впаде лише при підключенні (L02) з менш очевидною помилкою драйвера. Regex — один рядок; `@IsUrl()` тут не годиться (вимагає TLD, не приймає `localhost`/`db`), і це правильно помічено в обох варіантах.
- **Чому так в еталоні:** fail-fast має ловити і «не той формат», а не лише «відсутнє».
- **Коли твій кращий:** практично ніколи — хіба якщо в майбутньому зміниться драйвер.
- **Вердикт:** **розглянь еталон** — один декоратор, який відповідає ідеї fail-fast.

### 3.5. `cache: true` у `ConfigModule.forRoot`

- **Твій:** без `cache`. **Еталон:** `cache: true` — `ConfigService.get` не перечитує `process.env`.
- **Вердикт:** **рівноцінно** для L01 (виграш мікроскопічний). Можна додати одним рядком, якщо хочеш.

### 3.6. Назва функції валідації: `validate` vs `validateEnv`

- **Твій:** `export function validate(...)`. **Еталон:** `validateEnv` (і клас `Env` замість `EnvironmentVariables`).
- **Trade-off:** `class-validator` теж експортує `validate` — у файлі, що імпортує обидва, буде конфлікт імен або плутанина при читанні. `validateEnv` однозначна; знадобиться і в `data-source.ts` (див. 3.2).
- **Вердикт:** **розглянь еталон** (лише перейменування).

### 3.7. Compose: порт `db`

- **Твій підхід:** жорстко `'127.0.0.1:5434:5432'` — бо на твоїй машині 5432 зайнятий Homebrew-Postgres.
- **Еталон:** `'${DB_HOST_PORT:-5432}:5432'` — 5432 за замовчуванням, перевизначається змінною без правки файлу.
- **Trade-offs:** твій варіант прив'язує закомічений файл до однієї машини. Наслідок уже зараз: кореневий `.env.example` має `DATABASE_URL=...localhost:5432/chat_dev`, тож на свіжому клоні `cp .env.example apps/api/.env` → застосунок піде на 5432, а `db` слухає 5434 (у тебе — мовчки в локальний Homebrew-Postgres, бо там теж є 5432). Порт хоста — налаштування машини, а не проєкту.
- **Чому так в еталоні:** файл однаковий для всіх, локальна особливість — у змінній оточення.
- **Коли твій кращий:** якщо проєкт лише твій і лише на цій машині — але тоді все одно треба синхронізувати `.env.example`.
- **Вердикт:** **розглянь еталон** — `${DB_HOST_PORT:-5432}` у compose, а `export DB_HOST_PORT=5434` у своєму shell-профілі (і `5434` лише в особистому `apps/api/.env`).

### 3.8. Compose: прив'язка до `127.0.0.1`

- **Твій:** `127.0.0.1:PORT:5432` для обох сервісів. **Еталон:** без адреси — Docker публікує на `0.0.0.0`, тобто база видна всім у мережі (кав'ярня, офіс) з паролем `postgres`.
- **Вердикт:** **твій кращий.** Варто поєднати з 3.7: `'127.0.0.1:${DB_HOST_PORT:-5432}:5432'`.

### 3.9. Compose: YAML-якорі (`x-postgres: &postgres` + `<<: *postgres`)

- **Твій:** спільний шаблон (образ, креденшіали, healthcheck), сервіси задають лише відмінності; healthcheck параметризований `$${POSTGRES_DB}`.
- **Еталон:** свідомо без якорів — два сервіси повністю розписані, читаються без стрибків по файлу; `-d chat_dev` / `-d chat_test` у healthcheck явно.
- **Trade-offs:** якорі прибирають дублювання (зміна версії образу — в одному місці), але вимагають знати YAML merge keys і `$$`-екранування. Для двох сервісів виграш невеликий; у L03 (`compose.yml` з `migrate`/`api`) шаблони стануть кориснішими.
- **Вердикт:** **рівноцінно, лиши своє.** Обидва варіанти перевіряють потрібну БД у healthcheck (`-d`), тож `up --wait` чекає саме на `POSTGRES_DB`.

### 3.10. `configureApp` і префікс

- Збігається з еталоном: `setGlobalPrefix('api')` + `enableShutdownHooks()` у `configureApp`, `main.ts` — лише bootstrap і `listen(port)` з провалідованого конфігу. **Нічого міняти.**

## 4. Порівняння з Express

| Тема | Express | Nest (твоє рішення) |
|---|---|---|
| Маршрут + префікс | `router.get('/health', h)`, `app.use('/api', router)` | `@Controller('health')` + `@Get()`, `app.setGlobalPrefix('api')` |
| Graceful shutdown | вручну `process.on('SIGTERM', () => server.close(...))` + закриття пулів | `enableShutdownHooks()`; закриття ресурсів — у `onModuleDestroy` провайдерів (L02) |
| Конфіг | `dotenv` + `envalid`/zod на початку `server.ts`, об'єкт `config` імпортується скрізь | `ConfigModule.forRoot({ validate })` на імпорті модуля; `AppConfigService` інжектиться — по суті твій `config.ts`, але через DI |
| Тестовий застосунок | `createApp()` для supertest | `configureApp(app)` — та сама ідея: тести і прод конфігуруються однаково |
