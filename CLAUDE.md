## Команди студента

### `review lesson N` — рев'ю (протокол R1, розд. 5.2)

1. Перевірки: `npm run lesson:check -- N` (для занять з infra/деплоєм — `--full`) на `lesson/NN`.
2. Diff: `git diff lesson-NN-solution lesson/NN -- apps/api infra .github`.
3. Запиши `course/lesson-NN/review.md`: (1) результати перевірок; (2) blockers; (3) **порівняння підходів** по темах — твій підхід → підхід еталона → trade-offs → чому так в еталоні → коли твій варіант кращий → вердикт (лиши своє / розглянь еталон / рівноцінно); (4) порівняння з Express, де корисно; (5) що варто взяти з еталона (опційно).
4. Чекліст (blocker, якщо ні): тести `apps/api/test/lessons/**` не змінені студентом; є власний edge-case тест (з L05); міграції сумісні з попереднім образом (з L04, expand → contract); `check-architecture` зелений; нові ендпоінти в OpenAPI (з L05); секрети не в коді/логах/образах.
5. Пояснюй **різницю в підходах**, а не лише список правок. Код студента не переписуй — пропонуй.
6. Пройдено → статус `reviewed` у `PROGRESS.md`.

### `hint LNN.SK` — підказка (протокол H)

Рівні — по черзі, наступний лише на повторний запит: **рівень 1** — натяк (концепт, посилання на документацію); **рівень 2** — напрям (конкретний API Nest/TypeORM, структура без коду); **рівень 3** — конкретика (фрагмент для місця, не повне рішення). Ніколи не цитуй еталон дослівно. Запиши в `course/lesson-NN/hints.md`.

### «LNN закрито, згенеруй наступне» — генерація (протокол G1–G3, розд. 5.2)

- **G1:** у `PROGRESS.md` попереднє заняття = `closed`; прочитай фактичний код `main` і drift log. Інакше — не генеруй, скажи чому.
- **G2:** гілка `lesson/NN` від `main`; коміт `course(lNN): materials + red tests`; annotated `git tag -a lesson-NN-start`. Генеруй **лише одне** наступне заняття.
- **Тести — лише поведінкові:** HTTP (supertest на `createTestApp()`), SQL через `test/support/db.ts`, CLI-процеси, файлові контракти. Зі `src/` імпортуються лише фіксовані точки: `AppModule` (`src/app.module.ts`), `configureApp` (`src/app.setup.ts`), з L02 — `src/database/data-source.ts`. Заборонено `jest.spyOn`, `overrideProvider`, `app.get()`, unit-тести внутрішніх класів. Назви сервісів/модулів/файлів обирає студент.
- Тести на старті червоні **на assertion** (без `TS\d{4}`, `Cannot find module`, `SyntaxError`, `[course]`).
- **G3:** еталон пишеться в `git clone` у scratchpad (не worktree, без змін у репо студента), на ньому `lesson:check -- N --full` зелений; потім `git fetch <clone> lesson-NN-solution:lesson-NN-solution`; клон видалити. Compose у клоні — лише з `-p chat-it-<rand>`. Еталон не регенерується.
- Онови `PROGRESS.md` (SHA, результат G3).
- Зміна тестів попередніх занять — лише окремим комітом `test(lNN): contract migration — <причина>` + запис у drift log.

## Машинерія курсу — відповідальність генератора (розд. 5.5)

Якщо ламаються `lesson-check`, `check-architecture`, `check-ci-parity`, git hooks, `test/setup|support`, фікстури, guard-и, згенерований фронт — це баг курсу, а не завдання студента: окремий коміт `fix(course): …` на поточній гілці заняття, cherry-pick у `lesson-NN-solution`, запис у drift log `PROGRESS.md`, повторна перевірка (старт — red на assertion, еталон — green).

## Ніколи

- Не пушити `lesson-*-solution` (є pre-push hook і ruleset) і не використовувати `git push --all`/`--mirror`.
- Не показувати еталон і не цитувати його до рев'ю.
- Не писати бекенд-код студента без його прохання (фронт `apps/web` генерується курсом).
- Не створювати зовнішні ресурси (GitHub-репо, push, Hetzner, Cloudflare, секрети) без явної команди студента.
- Не комітити секрети; `.env` — лише локально, секрети CI — у GitHub Secrets.
- Не порівнювати з Java/Spring — студент з ними не працював; порівняння — з Express.
